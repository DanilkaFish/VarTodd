Mutate a Python tuner for VarTODD/FastTODD policy search on the selected GF matrix.
The objective is the lowest reliable final T-count rank. Lower is better.
`INITIAL_RANK` and `TARGET_FINAL_RANK` are provided by `helper.py`.

## 1. Hard contract

Produce one runnable Python evaluator.

- Define exactly one `Evaluator(BaseEvaluator)` and one module-level `entrypoint()`.
- Preserve the public helper API and use only libraries already installed in the runner.
- Do not install packages, access the network, hard-code a matrix path, or hard-code a matrix-specific rank.
- Keep `red` and `bucket` raw; normalize only the other features using the documented local normalizers.
- A larger sample budget, source pool, beam, seed count, or bucket cap is justified only when it buys useful actions, diversity, or rank progress.
- `entrypoint()` loads the selected matrix through `Evaluator(path_name="init", ...)`, runs the search, and returns `get_best()`.

Selection priority:
1. valid execution;
2. lower reliable final rank;
3. lower runtime only when rank evidence is not worsened.

The evaluator has two useful start modes. A fresh builder starts from
`path_name="init"` and must discover a complete descent. A refiner starts from a
currently selectable Live Path Store path and must beat that path's final rank.
Keep both modes represented across an evolutionary population when the parent
archive supports them. A single child can specialize in one mode; this is a
population balance target, not a per-program requirement.

Runtime is evidence, not the objective by itself. A cheap child is useful when it
buys more independent evaluations, seeds, or restarts within the same wall-clock
budget, or when it is a deliberate scout followed by a measured refinement. A
slow child is justified when its additional search produces rank progress or
exposes a new action family. Report the rank/runtime tradeoff explicitly.

## 2. Mutation protocol

Inspect the parent evaluator and its evidence before editing: rank path, accepted source
counts, pool fill, unique y counts, researched buckets, runtime, and optimizer history.
Choose one dominant failure mechanism. Keep the change attributable to that mechanism.

Every child should provide:

```text
Hypothesis:      observed bottleneck and why the change addresses it
Evidence:        concrete parent metrics
Mechanism:       score, sampling, source, restart, beam, or optimizer change
Runtime effect:  cost multiplier expected to change
Rank effect:     expected effect on action quality or path diversity
Fallback:        next mechanism if the hypothesis is falsified
Validation:      commands and observed rank/runtime result
```

Prefer structural changes when recent parents share the same score shape and source
schedule. Prefer score changes when generation is diverse and pools are full but final
choices are poor. Prefer sampling/source changes when pools are underfilled or positive
actions are rare. Preserve mechanisms that produce useful rank progress.

First-pass diagnosis:

| Observation | First mechanism to mutate |
|---|---|
| TOHPE pool underfilled | TOHPE y/z sampling or target band |
| TODD costs most time without rank gain | TODD bucket coverage or retention |
| Full pool but repeated actions | score shape, source mix, or beam selection |
| Small null-space dimensions | change z coverage or restart; do not increase y requests |
| Improvements stop early | restart point, schedule, or optimizer structure |
| Improvements continue late | allocate more evaluations or depth |

Use this table as a starting diagnosis, then verify it against counters. The
same symptom can have different causes: an empty pool can mean too little
sampling, a target band that rejects useful reductions, or a null space whose
dimension has already collapsed. Change one dominant mechanism at a time so a
child's result remains interpretable.

## 3. Search mechanics

Each policy step generates actions from TOHPE and TODD, ranks source pools with the
exploration score, merges them, ranks the merged pool with the finalization score, and
uses `ActionSelection` to expand selected actions. A seed repeats steps while positive
rank reductions remain.

An action is a pair `(z, y)`. `z` defines a bucket/binary null space and `y` is sampled
inside it. Only positive rank reductions are selectable.

For one state, the evaluator performs the following logical phases:

1. Construct or reuse the source search objects for the current rank.
2. Generate TOHPE candidates and retain up to its source-pool limit.
3. Research TODD buckets, generate candidates in each bucket, and retain its limit.
4. Apply the exploration score while filling source pools and merging them.
5. Apply the finalization score to the merged action pool.
6. Select one or more actions according to the action-selection policy.
7. Apply the selected rewrite and repeat from the new rank.

The implementation may stop a phase early when its pool is full, when no useful
positive action remains, or when the configured bucket policy has reached its
stopping condition. Consequently, configured maxima are upper bounds on work;
the counters from a run are the right way to estimate actual work.

### SamplingBudget

```python
SamplingBudget(
    one_hot=ONE_HOT_BUDGET,
    sparse=SPARSE_SAMPLES,
    dense=DENSE_SAMPLES,
    sparse_max_weight=SPARSE_MAX_WEIGHT,
)
```

`one_hot="all"` tries every weight-1 basis vector; an integer caps the number sampled.
Sparse and dense requests sample additional vectors. Sampling is de-duplicated within a
null space. A dimension-`dim` binary null space has at most `2**dim - 1` nonzero vectors,
so requests above that bound add no coverage. `one_hot="all"` contributes at most `dim`
vectors.

`one_hot` is useful when low-weight directions are likely to contain an action. It
does not enumerate the entire binary space: even with `"all"`, only the basis
vectors are forced. `sparse` adds random low-weight combinations, with
`sparse_max_weight` controlling the largest requested weight. `dense` adds
vectors with broader support. Increasing all three fields is wasteful when the
null space is small or when the source pool is already full.

Sampling is performed separately for every null space. A request that is large
relative to one `dim` can be saturated there and still be useful in another,
larger `dim`. Inspect unique-y counters by rank band before changing budgets.

### Sources

```python
TohpeSearch(
    SamplingBudget(...), SourcePool(...),
    z_choices=TOHPE_Z_CHOICES,
    target_min_red=TARGET_MIN_RED,
    target_max_red=TARGET_MAX_RED,
)

ToddSearch(
    SamplingBudget(...), SourcePool(...),
    actions_per_bucket=ACTIONS_PER_BUCKET,
    buckets=ZBucketSearch(
        min_buckets=Z_MIN_BUCKETS,
        max_buckets=Z_MAX_BUCKETS,
        limit_bucket=Z_LIMIT_BUCKET,
    ),
)
```

TOHPE samples y in the common binary null space and selects `z_choices` z candidates.
Its target-band distance is:

```text
max(target_min_red - red, red - target_max_red, 0)
```

Distance zero means `red` is inside the band. Smaller distance wins; equal distances
prefer greater reduction, then a stable key. This ordering happens before exploration
scoring. With an unbounded band, it reduces to descending reduction.

TOHPE's basis dimension is constant during one policy step: every TOHPE candidate has
the same `dim` and `ndim`. Those knobs cannot distinguish TOHPE candidates during
exploration, although they can matter across sources, states, or finalization.

This invariant matters when designing scores. A term whose value is constant for
all TOHPE candidates only shifts their common score; it cannot change their order.
Use TOHPE-varying terms such as `red`, `yw`, `zw`, target-band effects, or stable
candidate identity when separating TOHPE actions. Dimension terms remain useful
for comparing TOHPE with TODD, for schedules across ranks, and for finalization
when the merged pool contains different source or state dimensions.

TODD researches z buckets, builds a binary null space per researched bucket, samples y,
and retains up to `actions_per_bucket` actions per bucket. TODD can find actions TOHPE
misses, especially in difficult late-rank regions, but is much more expensive.

`ZBucketSearch.min_buckets` is guaranteed research. `max_buckets` is a soft reserve cap
(`0` means no soft cap). `limit_bucket` is a hard cap (`-1` means the full bucket space,
`buckets_space = rank**2 + rank`).

Finite bucket limits trade coverage for throughput. A small limit can expose fewer
rare actions but may permit more optimizer evaluations or independent seeds. A
large limit improves the chance of finding a useful late-rank action but can
consume the entire evaluation budget. `max_buckets` is not a promise that all of
those buckets will be researched: early pool saturation or stopping rules can
finish first. `min_buckets` is the reliable lower bound on research when the
source is enabled.

### Pools and selection

```python
SourcePool(keep=SOURCE_KEEP, reserve=SOURCE_RESERVE)
ActionPool(final_size=FINAL_POOL_SIZE)
ActionSelection(beamwidth=BEAMWIDTH, mode=SELECTION_MODE, temperature=TEMPERATURE)
```

`keep=0` disables a source. `reserve` protects actions for the final merge. `final_size`
caps the merged pool. `beamwidth=1` is a single-action descent. `mode="best"` is
deterministic; `mode="softmax"` uses `temperature` for stochastic selection.

`keep` controls source retention after candidates have been scored. Raising it is
useful only when the source can generate distinct positive actions and the merged
pool can consume them. `reserve` keeps a minimum contribution available for the
merge; it is not an additional generation budget. `final_size` controls how many
merged candidates reach finalization. If many candidates are generated but the
final pool is small, final-score changes may have little effect because candidates
are discarded earlier.

Beam selection changes trajectory branching, not candidate generation. A larger
beam can preserve alternatives but multiplies downstream state work. Softmax
temperature should be nonnegative; temperature zero or `mode="best"` gives
deterministic selection. Use stochastic selection when repeated actions or
optimizer convergence suggest that deterministic choice is collapsing diversity.

## 4. Policy expressions

Decorate ordinary Python functions with `@policy.exploration` and `@policy.final`.
They receive `(k, p, fn)`. `k` contains named knobs, `p.w(i)` declares free scalars in
contiguous order, and `fn` provides math functions (`exp`, `log`, `sqrt`, `tanh`,
`sigmoid`, `abs`, `floor`, `sign`, `min`, `max`, `pow`, `clip`, `where`, `not_`).
Both arms of conditionals are evaluated; guards must be explicit.

The exploration score ranks candidates while source pools are filled and merged. The
finalization score ranks the merged pool and determines which action is taken. Neither
score predicts future actions.

Reduction and bucket features are raw. Other normalized features use local normalizers.
The public knobs are:

| Site | Knob | Meaning and use |
|---|---|---|
| Both | `red` | Raw positive rank reduction of this action. Larger values are usually better, but a target band can deliberately prefer intermediate reductions. |
| Both | `dim` | Binary null-space dimension for the candidate. It controls possible y coverage and often correlates with evaluation cost. |
| Both | `ndim` | Dimension normalized by the local rank-dependent denominator. Useful for comparing states; constant across TOHPE candidates in one step. |
| Both | `bucket` | Raw TODD bucket identifier. It is an identity/location feature, not a reduction and not a probability. |
| Both | `yw` | Hamming weight or support size of y. It separates light and dense rewrites. |
| Both | `nyw` | y weight normalized by the y-vector width. Use it when absolute width changes across states. |
| Both | `zw` | Hamming weight or support size of z. It describes the bucket direction. |
| Both | `nzw` | z weight normalized by `zsize`. It is useful for comparing bucket shapes. |
| Both | `zsize` | Size of the z representation used for normalization. It is a denominator, not an action count. |
| Both | `max_red` | Largest reduction observed in the relevant candidate group or state. Compare with `red` to express relative opportunity. |
| Both | `source` | Source tag: `1` for TOHPE and `3` for TODD. Use it to learn a source preference in merged pools. |
| Both | `bucket_id` | Stable bucket index available for identity-sensitive tie breaking. Avoid treating it as an ordered quality score without evidence. |
| Both | `dn` | Local dimension/rank normalizer used by the helper. Do not infer a global constant from one matrix. |
| Both | `wvwn` | Local y-width normalizer used by the helper. It supports scale comparisons between states. |
| Final only | `tohpe` | TOHPE-specific candidate measure in the merged pool. It can distinguish final candidates even though TOHPE dimension is constant during generation. |
| Final only | `ntohpe` | `tohpe` normalized by the local dimension normalizer. |
| Final only | `rank_red` | Number of generated positive candidates with strictly greater `red`. Ties and the candidate itself do not count; the best reduction has rank zero. |
| Final only | `nrank_red` | `rank_red / max(1, population_size)`: the fraction of the generated positive population with strictly greater reduction. |
| Final only | `rank_dim` | Number of generated positive candidates with strictly greater basis dimension. Constant dimensions within a TOHPE-only step give zero. |
| Final only | `nrank_dim` | `rank_dim / max(1, population_size)`, using the same generated population as the raw rank. |
| Final only | `rank_score` | Number of generated positive candidates with strictly greater exploration score. This is a count, not the exploration score itself. |
| Final only | `nrank_score` | `rank_score / max(1, population_size)`, using the same generated population as the raw rank. |
| Final only | `population_size` | Number of all generated positive candidates before source-pool truncation, final-pool truncation and state deduplication. The denominator for every `nrank_*`. |
| Final only | `pool_size` | Number of candidates in the finalized merged pool. It indicates selection pressure and saturation. |
| Final only | `pool_tohpe` | Number of finalized candidates originating from TOHPE. |
| Final only | `pool_todd` | Number of finalized candidates originating from TODD. |
| Final only | `f_tohpe` | TOHPE fraction of the finalized pool. |
| Final only | `f_todd` | TODD fraction of the finalized pool. |
| Final only | `k_idx` | Candidate position/index in the finalization context. Treat it as an ordering feature. |
| Final only | `l_idx` | Additional local index for finalization ties or lookahead context. |

`ndim = dim / dn`, `nyw = yw / wvwn`, `nzw = zw / max(1, zsize)`, and
`ntohpe = tohpe / dn`. Each `nrank_*` divides its strict rank by
`max(1, population_size)`; each `f_*` divides its source count by
`max(1, pool_size)`. Generated candidates that are later discarded or lead to
the same state still count in the rank population. Raw `red` and `bucket`
intentionally remain in their original scale.

Do not add a second normalization layer in the policy expression. A hand-written
division by a guessed rank, matrix width, or population statistic can make a
score unstable across matrices. If a center or threshold is needed, bind it as a
searched parameter in the same scale as the feature and document that choice.

Bind parameters in `policy_mapping` and pass bound scores through `set_scores`:

```python
@policy.exploration
def explore_score(k, p, fn):
    return k.red * p.w(0) + k.bucket * p.w(1) + k.ndim * p.w(2)

@policy.final
def final_score(k, p, fn):
    return k.red * p.w(0) + k.ntohpe * p.w(1)

self.set_scores({
    "exploration": explore_score.bind([...]),
    "final": final_score.bind([...]),
})
```

Use `describe_knobs()` when in doubt. A score parameter vector must contain exactly
`n_params` values in `p.w(i)` order.

Good score mutations are interpretable. A linear score is a useful baseline. A
product can express interactions such as reduction conditioned on dimension. A
bounded transform (`tanh`, `sigmoid`, or `clip`) can prevent one raw feature from
dominating. A centered penalty can prefer a target reduction or a preferred
weight. Keep expressions short enough that a parent metric can falsify the
hypothesis.

For example, a score can reward reduction while penalizing unusually large y:

```python
@policy.exploration
def explore_score(k, p, fn):
    return k.red * p.w(0) + k.nyw * p.w(1) + fn.abs(k.red - p.w(2)) * p.w(3)
```

Here `p.w(2)` is a reduction center and should be searched over plausible raw
reduction counts, while `p.w(1)` can be one-sided if y weight must be penalized.
An expression parameter is not automatically normalized or constrained by the
compiler; choose its optimizer range to match its semantic role.

The exploration and finalization vectors are independent. A feature can have a
useful exploration effect while being irrelevant at finalization, or the reverse.
Do not copy a large parent expression solely because it contains many terms.
Remove terms whose converged weights are near zero or whose feature is constant in
the relevant pool, unless the term is intentionally retained for another regime.

Conditional expressions are branchless selects: both arms are evaluated. Write
safe denominators with `max(1, denominator)` or use `clip` before division. The
expression language rejects loops, comprehensions, lambdas, and arbitrary calls;
keep all nonlinear operations within `fn.*` and ordinary arithmetic.

## 5. Cost and saturation

Estimate one policy step from actual work:

```text
C_step ~= C_setup + N_H*C_tohpe + sum_j(C_bucket_j + N_T,j*C_y)
          + C_pool_score + C_final_lookahead
stage_time ~= E * ceil(S / W) * D * B * C_step
```

Use actual unique y counts and actual researched buckets when available. In low
dimensions, y sampling saturates at `2**dim - 1`.

With TODD disabled, TOHPE is the effective low-sampling regime. Enabling TODD introduces
large precomputed data structures. Their precomputation cost is typically comparable to
a complete TOHPE stage, approximately 1,000–10,000 bucket-research units. Total TODD
cost is precomputation plus actual bucket research; expensive runs commonly research
roughly 5,000–20,000 buckets depending on caps and stopping rules. Reducing TOHPE
sampling while TODD is enabled usually does not remove this dominant cost.

The useful accounting questions are:

- How many policy steps did each seed execute?
- How many TOHPE y vectors and z choices were actually evaluated per step?
- How many TODD buckets reached the research limit before a pool stopped the search?
- How many y vectors were unique after de-duplication?
- How many candidates survived each source pool and the final merge?
- How many seeds, workers, and optimizer evaluations shared the wall-clock budget?

For a fixed rank band, compare children using these measured quantities rather
than configured maxima. A child that halves `dense` but still researches the same
TODD buckets may have almost unchanged runtime. A child that reduces a bucket cap
can be faster, but only if the lost coverage does not remove the actions needed
for the target rank. A child that raises a source pool can be neutral when the
source produces fewer positive actions than the old pool already retained.

Sampling saturation is a correctness-preserving optimization opportunity. If
`2**dim - 1` is below the requested number of nonzero y vectors, further requests
cannot add a new y. In that case spend the saved budget on a different z, a
different source, or another seed. Saturation is local to each null space, so do
not generalize from one bucket to every rank band without checking counters.

The cost model also explains why a nominally small policy can be slow: setup,
matrix transforms, score evaluation, pool maintenance, and final lookahead add
fixed work to every step. Measure per-step time at representative early, middle,
and late ranks. A change that helps only a saturated early band may not improve
the full trajectory.

## 6. Evaluator lifecycle and restarts

```python
Evaluator(
    path_name="init",
    init_rank_thr=None,
    fin_rank=TARGET_FINAL_RANK,
    margin=REOPEN_MARGIN,
    max_depth=MAX_DEPTH,
)
```

`path_name="init"` loads the selected matrix. A live path name loads and branches a
saved path. `loaded_path_rank` is the parent's final rank; a refiner must beat it.
`loaded_rank` is the child's actual starting rank after branching.

`map_par(mapping, group="name")` declares optimizer parameters. Group declaration order
must be stable; use `select_parameter_groups(...)` only before constructing the optimizer.
After a restart or reinitialization, query `extract_active()` again and rebuild optimizer
state if the active dimension changed.

`run(params, seeds)` evaluates the current parameter vector. `set_up_new_init(path_num,
rank_thr, xopt=None)` branches an in-memory best path and returns the new active vector or
`None`. `get_best()` is called once at the end of `entrypoint()`.

Use `extract_active()` as the source of truth for the optimizer vector. The
parameter vector contains only currently selected groups, while `x0` may contain
all mapped values. A mapping callback should be deterministic for a given input
and should not mutate evaluator state. Keep group names stable across children so
optimizer histories remain comparable.

When constructing a schedule, rank breakpoints are evaluated from high rank to
low rank. A schedule point applies until the next breakpoint; use a small number
of meaningful phases instead of many adjacent points that differ only slightly.
Schedule changes are structural mutations and should be reported separately from
score-weight changes.

Restarting from a saved path changes the matrix state, rank context, and often the
useful feature ranges. Recompute rank-span constants and inspect the new counters
after every restart. A restart that starts too close to the saved final rank may
have no room to improve; a very large margin may repeat work already present in
the path.

## 7. Evidence and mutation decisions

Read `path_policy_groups`, `converged_policy_profiles`, and `search_stat` together.
Compare configured values with actual values:

- configured source keep/reserve versus accepted TOHPE/TODD counts;
- configured final pool versus actual pool size;
- configured sampling versus actual unique y counts;
- configured z limits versus actual researched buckets;
- optimizer evaluations versus last improvement and repeated-best count.

Read the rank path as a sequence, not only its final value. A long early descent
followed by a flat tail points to a different mechanism than a run that stalls
immediately. For each rank segment, record the first and last improvement, the
number of positive actions, and the source of accepted actions. Compare repeated
best actions with the final pool size to detect deterministic collapse.

Interpret common evidence as follows:

| Evidence | Likely interpretation |
|---|---|
| Source pool below `keep` | Generation, positivity, or target-band filtering is limiting supply. |
| Source pool full but few unique actions | Retention or scoring is collapsing diversity. |
| Many researched buckets but few positive actions | Coverage is expensive without useful yield; alter bucket policy or source mix. |
| Positive actions exist but final choice is weak | Finalization score, source balance, or beam selection is misaligned. |
| Unique y count equals the binary-space bound | Sampling is saturated; spend work on z, TODD, or seeds. |
| Same policy profile dominates recent parents | Evolution is converging; mutate schedule, source mix, or restart context. |
| Improvements continue at the evaluation limit | More evaluations may buy rank; justify their cost with the observed slope. |
| No improvement after a restart | The branch threshold, parameter group, or budget may be wrong. |

Check whether an apparent insight is causal. For example, “larger dimension is
better” may simply mean TODD supplied the candidate, or “more buckets is better”
may reflect a different rank band. Compare matched runs or parent metrics before
turning such observations into a score term.

Underfilled pools or rare positive actions indicate generation/coverage problems. Full
pools with repeated actions indicate diversity or scoring problems. Small dimensions mean
y requests are already saturated. A segment with no late improvements is a restart or
optimizer problem; improvements continuing near the budget justify more budget.

Use Live Path Store names currently listed as selectable. Small margins refine a tail;
larger margins reopen an earlier branch. Do not load names from lineage, hidden paths, or
old backups unless they are currently selectable.

Return a short report with the mutation hypothesis, evidence, changed mechanism, files,
validation result, and runtime/rank tradeoff.
