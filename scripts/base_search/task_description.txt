Find a Python tuner that minimizes T-count by tuning a FastTODD policy.

Known target: at least 385 T-count is reachable.
n=48.

---
## Goal
- Matrix rank equals T-count; lower final rank is better.
- Runtime is part of the search trade-off. Target about `1500` seconds when possible.
- Programs expected to run above `3000` seconds are high-risk because timeouts lose useful evaluations.
- A program is useful only if `entrypoint()` returns `fun.get_best()`.
- If a persisted path is loaded, the final rank must be strictly below the loaded path rank; otherwise validation penalizes it.
- Do not judge a run only by reduction per step. The objective is the lowest reliable final rank within runtime, not the fewest FastTODD steps.

---
## FastTODD Mechanics And Cost
- FastTODD searches actions `a = (z, y)`, where `z` is a boolean vector and `y` comes from a nullspace `N_z`.
- TOHPE-stage action generation uses a reduced search space. Its setup cost is about `O(n^2 * m^2)`.
- TODD-stage researches candidate `z` buckets, builds `N_z`, then emits coefficient vectors by explicit sample caps.
- Coefficient sampling is controlled by `SamplingBudget(one_hot, sparse, dense, sparse_max_weight)`.
  - `one_hot`: basis vectors of weight 1. Use `one_hot="all"` to try every one-hot basis vector.
  - `sparse`: random coefficient vectors with weight in `[2, sparse_max_weight]`.
  - `dense`: random bitvectors in the current basis dimension.
- TOHPE and full TODD have independent `SamplingBudget` values inside `TohpeSearch` and `ToddSearch`.
- TODD search complexity scales with researched z buckets; high `max_buckets` raises the reserve-target search cap.
- `beamsearch_width` and `todd_width` scale roughly linearly.
- `ZBucketSearch.min_buckets` is guaranteed z-bucket research; `ZBucketSearch.max_buckets` caps reserve-target search, not total search when no action has been found.
- Large `researched_z_mean/max` means accepted reducing actions were found only after substantial search. This is evidence about difficulty, not automatically waste.
- `bucket_size * 2` is a possible maximum reduction for a chosen z; it is not guaranteed to exist.
- Increasing vector sample caps is usually cheaper than increasing z-search breadth. It mostly changes action diversity and quality inside the current z budget.
- One objective call may run many FastTODD steps.
- !!! Each program can parallelize seed evaluations up to 3 workers inside `fun.run(params, seeds)`. More than 4 seeds run in batches and remain a runtime multiplier.
- Runtime is multiplied by optimizer evaluations, seed count, `beamsearch_width`, `todd_width`, source pool sizes, z-search limits, vector sample caps, and path depth.
- To avoid timeouts, estimate cost from previous `runtime`, `total_eval`, path depth, and `path_policy_groups` before increasing expensive knobs.

## Policy Knobs
Budget and action generation:
- `SamplingBudget(one_hot, sparse, dense, sparse_max_weight)`: coefficient-vector budget for one source.
- `SourcePool(keep, reserve)`: max candidates kept from one source and minimum reserved before final merge. Set `keep=0` to disable that source.
- `TohpeSearch(sampling, pool, z_choices)`: TOHPE-stage candidate generation.
- `ToddSearch(sampling, pool, actions_per_bucket, buckets)`: full TODD-stage candidate generation.
- `ZBucketSearch(min_buckets, max_buckets, temperature, random_fraction)`: guaranteed z-bucket research, reserve-target search cap, and bucket-order randomness.
- `ActionPool(final_size)`: retained action pool after source merge and final scoring.
- `ActionSelection(count, mode, temperature)`: number of actions followed per step, final-choice mode, and softmax temperature.
- `beamsearch_width`: number of states kept after each step.
- `todd_width`: number of actions followed per step.
- `ToddSearch.actions_per_bucket`: action cap from one researched z bucket.

Removed legacy knobs:
- Do not use flat policy setters or keys such as vector sample caps, pool sizes, min actions, z limits, temperature, or per-z action limits.
- Do not use `num_samples`, `gen_part`, `try_only_tohpe`, `enable_tohpe`, `enable_todd`, `max_tohpe`, `tohpe_num_best`, `mix_*`, `vector_samples`, or `non_improving_prob`.
- Disable a source by setting `SourcePool(keep=0, reserve=0)` inside that source search object.
- For `path_store` reproduction, old C++ forced `gen_part=1.0`, so `num_samples=N` is closest to `SamplingBudget(one_hot="all", sparse=0, dense=N, sparse_max_weight=2)`. For older code that actually honored `gen_part=g`, use `SamplingBudget(one_hot=round(N*g), sparse=0, dense=N-round(N*g), sparse_max_weight=2)`, or add sparse budget explicitly.
- Candidate generation accepts only positive rank reductions. Zero and negative reductions are discarded.
- `min_buckets` is the guaranteed TODD z-bucket count. `max_buckets > 0` caps the search for TODD's reserve target; if no positive TODD action has been retained at that cap, scanning continues until one is found or all buckets are exhausted.

Scoring:
- `ExplorationScore(weights=[wred, wdim, wbucket, wvw, wz], centers=[...], pow=...)`
- `FinalizationScore(weights=[fwred, fwdim, fwbucket, fwvw, fwz, fwtohpe], centers=[...], pow=...)`
- Features: `red` = rank reduction, `dim` = sampled-space dimension, `bucket` = early z estimate of possible reduction, `vw` = y-vector Hamming weight, `z` = z-vector Hamming weight, `tohpe` = future TOHPE nullspace size.
- Higher score is better throughout candidate pooling, source merging, final choice, and beam pruning.
- `fwtohpe != 0` triggers an extra state application and TOHPE-basis recomputation for final candidates. Use only when that extra quality signal is worth the cost.

Scheduling:
- Any policy value can be constant or rank-scheduled.
- `set_X(constant)` applies one value everywhere.
- `set_X(ranks, values)` applies a rank schedule. Thresholds are sorted high to low.
- Example: `ranks=[300, 200, 100]`, `values=[A, B, C]` gives rank `350 -> A`, rank `250 -> B`, rank `50 -> C`.

No optimizer family, schedule shape, score-weight sign, parameter count, or restart pattern is preferred by this description. Use metrics, validation, path statistics, runtime, and code evidence to decide.

## Evaluator Contract
Each program must define:
- `Evaluator.policy_mapping()`
- `Evaluator.__call__(params)`
- `entrypoint()` returning `fun.get_best()`

Required API:
- `map_par(mapping=<callable>, thr=<int>)`: declares a tunable parameter, active only if `init_rank > thr`.
- `set_X(constant)`: set a constant policy value.
- `set_X(ranks: list[int], values: list[Any])`: set a rank schedule.
- `run(params, seeds) -> list[int]`: evaluates ranks for fixed seeds.
- `set_up_new_init(path_num, rank_thr, xopt) -> list[float] | None`: starts from a matrix in a current-run best path.
- `Evaluator.from_saved_path(path_name, rank_thr=None, margin=<number>, max_depth=...)`: starts from a persisted path. If `margin` is below 10 it is clamped to 10.
- `extract_active() -> list[float]`: returns the active parameter vector.

Current-interface examples:
- `self.set_scores(PolicyScores(exploration=pool_score, final=final_score))`
- `self.set_action_selection(ActionSelection(count=1, mode="softmax", temperature=0.15))`
- `self.set_action_pool(ActionPool(final_size=12))`
- `self.set_tohpe_search(TohpeSearch(sampling=SamplingBudget(one_hot="all", sparse=0, dense=32, sparse_max_weight=2), pool=SourcePool(keep=2, reserve=0), z_choices=4))`
- `self.set_todd_search(ToddSearch(sampling=SamplingBudget(one_hot=40, sparse=10, dense=30, sparse_max_weight=4), pool=SourcePool(keep=10, reserve=1), actions_per_bucket=2, buckets=ZBucketSearch(min_buckets=500, max_buckets=300000, temperature=0.15, random_fraction=0.03)))`
- `self.set_widths(beam=2, actions=1)`

Useful fields:
- `best_rank`: current best rank.
- `best_paths`: saved best paths from the current run.
- `path_num`: number of current-run reinitialization paths.

## Saved Path Reuse
- Saved path names must come from the current `## Live Path Store` prompt block.
- Only path names listed under `best_paths:` are allowed. Do not invent, remember, or reuse any other saved path name.
- `"init"` means no preloaded path.
- Loading forms:
  - `fun = Evaluator.from_saved_path("<path_name>", margin=<chosen_margin>, max_depth=...)`
  - `fun = Evaluator.from_saved_path("<path_name>", rank_thr=<chosen_rank>, max_depth=...)`
  - backward-compatible: `fun = Evaluator(path_name="<path_name>", init_rank_thr=<rank>, max_depth=...)`
- Path name format: `i<init_rank>_m<init_rank_thr>_f<final_rank>_<hash>`.
- Saved-path margins below 10 are clamped to 10.
- `live_restart_balance` counts live candidates by restart band: `from_init` (`m == i`), `first_half` (`m > (i+f)/2`), and `near_final` (`m <= (i+f)/2`).
- `used` is the number of reuse attempts.
- `improved` is the number of reuse attempts that improved the loaded rank.
- `best_child` is the best rank obtained after reusing that path.
- `parent`, `loaded_rank`, `parent_thr`, and `child_improved` describe the loaded path that produced a saved child, when known.
- `dead_end_paths:` lists at most 3 paths with too many failed reuse attempts.
- `best_nonimproved_child_paths:` lists at most 3 saved children that did not improve their loaded parent.
- `revived_dead_end=1` marks a historically risky path that is still present under `best_paths:` because it has some improvement evidence.

## Report Meanings
- `fitness`: primary objective; lower is better.
- `runtime`: execution time in seconds.
- `is_valid`: validation status.
- `search_stat`: rank improvements during the run.
- `total_eval`: FastTODD evaluation count.
- `best_seen_times`: number of times the best rank was found.
- `this path name`: persisted path from the current run.
- `## Live Path Store`: current global saved-path candidates, loaded fresh during prompt assembly.

Path statistics:
- `path_summary`: depth, init rank, final rank, total reduction, and rank trajectory.
- Prompt path statistics start from the largest matrix used as an active start before the best result, not necessarily the first loaded rank. The full stored path remains on disk.
- `path_policy_groups`: aggregate path statistics grouped by the active policy segment.
- Each group shows `ranks`, `steps`, mean selected reduction, mean available max reduction, selected `basis_dim` mean/max, selected `bucket` mean/max, and accepted-action counts split as TOHPE/TODD.
- `accepted_mean` and `accepted_min` summarize accepted TOHPE/TODD actions per policy iteration; `accepted_min` ignores terminal/no-action iterations where zero actions were accepted.
- `accepted_per_z_mean/min/max` is total accepted actions divided by researched z. It ignores terminal/no-action iterations and zero-denominator TOHPE-only/missing-total iterations; `n/a` means no positive researched-z denominator was available.
- `researched_z_mean/max`: number of z candidates actually researched by policy iteration, sourced from `Stats.total`.
- `policy={...}` inside each group shows the policy values active for that rank segment, including widths, budget/mode knobs, and compact `pool_scores`/`final_scores`.
- Compare each group's aggregate statistics against its `policy={...}` values; do not infer per-step behavior that is no longer printed.
